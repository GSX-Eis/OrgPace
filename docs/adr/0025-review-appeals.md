# ADR-0025：申诉以展示状态覆盖正式画像

状态：已接受（2026-11-26 由 NERE-1425 变更为仅保留历史只读与遗留收口）

> 注：以下第 1–3 段为 2026-11-26 规则变更前的原申诉设计背景；自 NERE-1425 起已取消新增申诉（含移除 MCP `appeal_decision`），现行规则见文末「2026-11-26 补充（NERE-1425，规则变更）」。

拒绝的改动可能没有对应的正式判断。申诉不能成为系统或管理员改正式画像的途径。

申诉按企业、员工和改动项记录。创建时锁定原请求，同项最多一个 open 申诉，并由数据库部分唯一索引兜底。当前画像按能力 key 计算「存在争议」，员工列表优先显示 disputed；历史版本不叠加当前申诉，ProfileClaim、版本快照和证据正文保持不变。

申诉原因及处理说明只向本人、原决定的 reviewer_user_id / acting_for_user_id 和本企业管理员开放，不沿用部门经理的普通可见范围。管理员维持决定或复制单项及证据引用到 correction 草稿，员工修改后走现有提交服务。处理与草稿、审计和通知在同一事务完成。申诉文本不写入证据或审计详情。

允许处理后再次申诉，同项仍最多一个 open 记录。管理员允许重新提交只生成草稿，不代表批准；新草稿照常适用企业审批规则。机器人不暴露该写工具，MCP 可以直接申诉。

2026-11-11 补充（NERE-305）：以申诉记录的 employee_id 识别提出人，管理员不能处理自己提出的申诉。共享服务在任何状态变更、草稿创建、审计和通知前返回 403，管理助手起草变更集时复用相同检查。列表和首页待办仍展示本人的申诉，网页禁用处理按钮并说明原因。企业只有一名管理员时不做例外，需要另一位管理员处理。

2026-11-26 补充（NERE-1425，规则变更）：取消被拒后发起新申诉的流程，改为查看拒绝原因后直接「修改重提」。
- 禁用新增申诉：`POST /orgs/{org_id}/appeals` 与 `appeal.appeal_decision` 统一返回 `410 Gone`（`已取消被拒申诉流程，请修改后重新提交`），不写库、不发通知、不写审计；MCP `EMPLOYEE_TOOLS` 移除 `appeal_decision`；前端移除所有「申诉」按钮与提交表单。
- 改为修改重提：整单被拒或部分被拒的请求在「我的画像 → 已处理请求」中标红展示拒绝状态与理由，员工通过「修改重提」复用已关联草稿或复制未批准项与有效证据创建草稿后重新提交（`save_draft(..., withdrawn_request_id=...)` 同步兼容 `REJECTED`、`CHANGES_REQUESTED` 与含被拒项的 `APPROVED` 来源请求）。
- 历史数据兼容：不删改 `review_appeal` 表（无新增 Alembic 迁移），保留 `GET /appeals/{appeal_id}`、`GET /appeals` 与 `POST /appeals/{appeal_id}/resolve`（保留禁止自裁检查）用于历史申诉只读展示与管理员关闭系统升级前遗留的 `open` 申诉。
